# Adjudication: integer divide-by-zero — the MICROWORD is right, both functional cores are wrong

**Full path:** `E:\Dev\Ronny\ND5000UC\ADJUDICATION-DIVIDE-BY-ZERO-2026-08-08.md`
**Date:** 2026-08-08
**Cluster:** ~184 of the 826 third-column divergences (`Nd500xCorpusSweepTests`, opcodes

## The disagreement

| | dest register on n/0 | DZ bit |
|---|---|---|
| corpus / functional CpuND500 / nd500x | UNCHANGED (keeps the seed) | set |
| microword CpuND5000 (real B30) | SATURATE — 0x7F for BY 100/0 | set |

## The verdict — manual and microcode agree, in the microword's favor

**ND-05.009.4 (DZ trap description, verified in the OCR'd manual at nd500x
`docs/ND-05.009.4 EN ND-500 Reference Manual.md:2049`):**

> "A division with zero will leave the largest possible value in the destination with the sign
> of the dividend, unless the dividend is also zero. Zero divided by zero gives a result of zero."

**The real B30 microcode implements exactly that** (traced live 2026-08-08 with
`Nd500xCorpus_TraceOneVector`, words read raw with mcread):

- DIVBY prologue @02420 seeds `SC2 := BM07` (the BY saturate magnitude source).
- DIV_INT @024131/024132 tests the divisor (`ALU,A A,SC7` → `COND,MZRO`).
- Zero path @024133 routes the saturate into SC3, @024134/024135 OR **BM14 = bit 12 = DZ**
  into the status (`ST,LOAD`) and RETURN+POP.
- The shared epilogue @02422 stores SC3 to the destination (`D,ALU,REG37 G,OOPS`) —
  deliberately, on BOTH paths.

Engine result for BY 100/0: dest = 0x7F, DZ set — byte-exact with the manual sentence.

**Why the functional side looked confirmed but wasn't:** the corpus is GENERATED by the
functional CpuND500 and nd500x was aligned TO the corpus — so "two cores agree" here was one
design decision ("leave dest unchanged"), copied twice. Not two independent confirmations.

## Consequences / the work

1. **Fix functional C# divide-by-zero** (`Emulated.HW ...Divide.cs` family): dest := largest
   value of the datatype with the dividend's sign; 0/0 := 0; DZ bit set (unchanged). Mind BY/H/W
   widths and UDIV.
2. **Fix nd500x the same way** (its `Div*.c` / `Udiv.c`).
3. **Regenerate the div-by-zero corpus cases** through the DualWriter flow, re-merge into
   `nd500_tests.json`.
4. Negative-dividend saturate value (largest NEGATIVE? 0x80 vs 0x81 for BY) must be read from
   the microcode's @024136/024137 (DZ+sign variant) or traced — do NOT guess the exact bit
   pattern when fixing the functional cores; run the microword on a negative-dividend case first.
5. Frame-log parity guard: the byte-exact compile does not exercise divide-by-zero (NC compiles
   fine today on the unchanged-dest cores), but rerun the parity check after the nd500x change
   anyway.

## Standing lesson

Corpus agreement is only as independent as its generators. Before trusting "two cores agree",
check whether one generated the other's expectations.
